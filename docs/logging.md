# Правила файлового логирования TNC-server

Версия: 1.0 (2026-09-16)

Файловое логирование пишет трафик устройств в подкаталог `logs/` рабочего
каталога сервера. Оно дополняет (не заменяет) операционные логи сервера и
web-просмотр логов по WebSocket.

---

## 1. Назначение файлов

Для каждого устройства за каждый день (UTC) создаётся пара файлов:

- `<DID>.txt` — человекочитаемый лог: только сообщения команды `0x59`,
  декодированные по `docs/auth/protocol/cmd0x59.md`;
- `<DID>.hex` — сырой hex-дамп: только **входящие** (IN) фреймы от устройства.

## 2. Расположение и структура каталогов

```
logs/                       ← корень логов (LOG_DIR, по умолчанию "logs")
  2026-09-16/               ← папка дня в UTC, имя строго YYYY-MM-DD
    N-10.txt
    N-10.hex
  2026-09-15/
    ...
```

- Папка дня создаётся автоматически при первой записи (`MkdirAll`, права 0755).
- Имя файла — `<DID><расширение>`, где DID — санитизированный Device ID:
  - допустимы латиница `A–Z a–z`, цифры `0–9`, символы `. _ -`;
  - любой другой символ заменяется на `_`;
  - пустая строка, `.` или `..` → `unknown`.
- Файлы открываются в режиме дозаписи (`O_CREATE | O_APPEND | O_WRONLY`,
  права 0644); содержимое существующего файла дня не обнуляется.

## 3. Жизненный цикл

- **Открытие** — при успешной авторизации устройства (после команды 0x65),
  одновременно с подпиской на hub.
- **Закрытие** — при разрыве соединения (включая idle timeout и ошибки чтения).
- **Смена суток** — при переходе через полночь UTC файл вчерашнего дня
  закрывается, открывается файл нового дня.
- Повторная авторизация в тот же день — запись продолжается в тот же файл.

## 4. Ограничение размера и срок хранения

- **Максимальный размер одного файла — 100 МБ** (`LOG_MAX_FILE_MB`, по
  умолчанию 100). Проверка — на границе строки, фрейм не разрывается. При
  достижении лимита текущий файл закрывается и открывается следующий по
  порядку в той же папке дня: `N-10.txt` → `N-10.2.txt` → `N-10.3.txt` …
  (механизм ATBridge с переименованием текущего файла в
  `<DID>.<YYYYMMDD-HHMMSS><ext>` не используется).
- **Срок хранения — 7 дней** (`LOG_RETENTION_DAYS`, по умолчанию 7): хранятся
  сегодня + 6 предыдущих суток (UTC). Папки дней старше границы удаляются
  целиком (`RemoveAll`).
- Чистка запускается при старте сервера и далее раз в сутки. Удаляются
  **только** каталоги, имя которых парсится строго как `YYYY-MM-DD`; файлы и
  каталоги с другими именами не трогаются.

## 5. Формат `.hex` — сырой дамп входящих фреймов

- Пишутся только входящие фреймы (IN, устройство → сервер). Исходящие (OUT,
  ретрансляция на другие устройства) **не пишутся**.
- Пишутся только фреймы с корректной CRC — фреймы с ошибкой CRC отбрасываются
  на уровне чтения кадра и в лог не попадают.
- Пишется фрейм целиком, как принят из сети: преамбула `0x24`, адрес, команда,
  длина (LE), данные, CRC.
- Формат строки (время UTC, миллисекунды):

```
2026-09-16 12:34:56.789 IN 24 76 59 2C 00 00 ... 5A
```

- Один фрейм — одна строка, окончание строки `\n`. Байты — hex в верхнем
  регистре, через пробел.

## 6. Формат `.txt` — декодированные сообщения 0x59

- Пишутся **только** сообщения команды `0x59`, принятые от авторизованного
  устройства с адресом `0x76` и корректной CRC. Другие команды (0x65 и пр.)
  в `.txt` не пишутся.
- Декодирование — по `docs/auth/protocol/cmd0x59.md`; порядок байт —
  little-endian, размер данных — 44 байта.
- Имена полей — **строго как в протоколе** `docs/auth/protocol/cmd0x59.md`.
- Формат строки — одна строка на сообщение, поля через двойной пробел:

```
2026-09-16 12:34:56.789  N-10  0x59  Номер_сообщения=12345  UTC=2026-09-16T12:34:56.789Z  iekf_hw_offset_1=+12.345000  iekf_hw_offset_2=+0.001000  iekf_hw_offset_3=-7.890000  static_cnt=10  validity=0b00000111
```

Пояснения к полям:

- Первая метка времени — момент **приёма сервером** (UTC, миллисекунды).
- `Номер_сообщения` — номер сообщения (`uint32`), десятичный.
- `UTC` — время сообщения из кадра (`uint64`, миллисекунды с эпохи Unix),
  выводится как ISO-8601 с миллисекундами, суффикс `Z`.
- `iekf_hw_offset_1` … `iekf_hw_offset_3` — смещения (`double`, метры).
  Фиксированно 6 знаков после запятой, хвостовые нули сохраняются, знак
  (`+`/`-`) выводится всегда.
- `static_cnt` — количество эпох в измерении (`uint32`), десятичный.
- `validity` — битовая маска валидности (`uint32`), выводится в двоичном виде
  (`0b` + 8 бит). Бит 0 (`1<<0`) — валиден `iekf_hw_offset_1`, бит 1 (`1<<1`) —
  `iekf_hw_offset_2`, бит 2 (`1<<2`) — `iekf_hw_offset_3`.
- Если слот невалиден (соответствующий бит `validity` сброшен), после значения
  добавляется пометка `(invalid)`, например:
  `iekf_hw_offset_2=+0.001000(invalid)`. На графике «Поправки» невалидные
  слоты **не отображаются**.

## 7. Надёжность и конкурентность

- Одна строка лога записывается атомарно; записи от разных соединений
  сериализуются — строки не перемешиваются.
- Ошибки записи не прерывают обработку трафика: сообщение уходит в стандартный
  лог сервера, соединение продолжает работу.
- Буферизация записи с принудительным сбросом после каждой строки (в пределах
  суток данные не теряются при остановке сервера).

## 8. Конфигурация

| Переменная          | По умолчанию | Назначение                             |
|---------------------|--------------|----------------------------------------|
| `LOG_DIR`           | `logs`       | Корень логов (относительно рабочего каталога сервера) |
| `LOG_RETENTION_DAYS`| `7`          | Срок хранения, суток                   |
| `LOG_MAX_FILE_MB`   | `100`        | Максимальный размер одного файла, МБ   |

- В `docker-compose.yml` каталог `logs/` монтируется volume'ом, чтобы файлы
  сохранялись между перезапусками контейнера.

## 9. Что сознательно НЕ логируется

- исходящие (OUT) фреймы — ни в `.hex`, ни в `.txt`;
- команды, кроме `0x59`, — в `.txt` (в `.hex` попадают все CRC-корректные
  входящие фреймы любой команды);
- фреймы с ошибкой CRC;
- web-логи (WebSocket-просмотр) — отдельный механизм, в файлы не дублируется.
